# CLAUDE.md — Rules for Claude Code on this project

This file governs how Claude Code should behave on the MonitovoPDF project.
Read [CONTEXT.md](CONTEXT.md) at the start of each session for project orientation.

---

## ⚠️ This repository is PUBLIC

Everything committed here is world-readable the moment it is pushed, and stays
readable in the git history even after deletion.

- **Never commit secrets.** No tokens, passwords, API keys, connection strings,
  certificates or private keys. Placeholder values (`YOUR_KEY_HERE`, `changeme`)
  are the only exception.
- Local secrets go in environment variables, `.env`, or `appsettings.Local.json`.
  All three are gitignored. The tracked `appsettings.json` and
  `appsettings.Development.json` hold non-secret structural config only.
- **Do not commit customer names, internal hostnames, licence keys or sample
  documents containing real data.** Test fixtures must use synthetic content.
- If a secret is ever committed, treat it as compromised: rotate it first, then
  deal with the history. Flag it immediately rather than quietly amending.

## Git & Commits

- **Never commit automatically.** Before running `git commit`, explicitly state:
  (1) the current branch name, (2) every file being staged, and (3) the proposed
  commit message. Then stop and wait for Joe to say yes. Do not proceed until
  confirmed. This is the highest-priority git rule.
- **Never push automatically.** Pushing to remote always requires explicit instruction.
- **Always verify the branch before staging anything.** Run `git branch --show-current`
  and confirm it is the intended branch before touching `git add` or `git commit`.
- **Work on a `feature/` or `fix/` branch and open a PR.** Do not commit directly to
  `main`. One PR at a time, based on `main` — no stacked PRs.
- **Never mention Claude, AI, or any AI tooling in commit messages, PR descriptions,
  issues or code comments.** No "Generated by", no "Co-Authored-By". Everything reads
  as if written by a human developer. This matters more here than on a private repo,
  because all of it is public.
- **Write meaningful commit messages** that describe *why* the change was made.

## Project Hygiene

- **Do not create files speculatively.** Only create files needed for the current
  task. Prefer editing existing files.
- **Keep [CONTEXT.md](CONTEXT.md), [PLAN.md](PLAN.md) and [TODO.md](TODO.md) up to date**
  when completing work that changes project state or priorities.
- **Remove dead code and leftover scaffolding** rather than commenting it out.
- **Do not invent new top-level directories without discussion.**
- **Keep the dependency list small and justify every addition.** Each NuGet package
  added to a public MIT project is a licence obligation, a supply-chain risk and a
  thing to keep patched. Check the licence of anything new before adding it — a
  copyleft or commercially-licensed PDF library is incompatible with shipping this
  under MIT.

## Configuration

- **All environment-specific values must come from configuration, never from code.**
  URLs, hostnames, ports, credentials, limits and feature flags.
- **The same build must run in every environment without code changes.** Standard
  ASP.NET Core layering, in increasing order of precedence:
  - `appsettings.json` — defaults and non-secret structural config
  - `appsettings.{Environment}.json` — per-environment non-secret overrides
  - `appsettings.Local.json` — untracked local overrides
  - Environment variables — secrets and deployment-specific values, `__` as the
    separator for nested keys
- **No magic numbers or hardcoded values.** Use configuration or named constants.
  Page sizes, timeouts, memory ceilings and concurrency limits are all configuration.

## Code Quality

- **Don't add features, refactors or "improvements" beyond what was asked.** Scope
  changes narrowly. Surface broader improvements as suggestions rather than doing
  them silently.
- **Don't add error handling for impossible cases.** Validate at system boundaries
  (HTTP inputs, file parsing, external calls). Trust internal contracts.
- **Write tests for the rendering pipeline and the HTTP surface.** These are the
  core of the product and must have coverage. A rendering change without a test
  that pins the output is not finished.
- **Nullable reference types and implicit usings are enabled.** Keep the build at
  zero warnings.

## Security

This is a service that accepts untrusted input and turns it into documents. That is
an unusually sharp attack surface. Treat these as hard requirements:

- **Never introduce command injection, path traversal, SSRF, XSS or other OWASP Top 10
  vulnerabilities.** If you spot an existing vulnerability while working, flag it
  immediately rather than quietly patching around it.
- **Treat every input document, URL, template and font as hostile.** Validate at the
  boundary. Never pass user-supplied values into a shell, a file path or a process
  argument without validation.
- **If HTML-to-PDF rendering is used, the renderer must not be able to reach the
  local network or the filesystem.** A renderer that follows user-supplied URLs is an
  SSRF primitive against whatever host it runs on.
- **Bound every operation.** Input size, page count, render time and memory all need
  explicit ceilings, or a single request becomes a denial of service.
- **Never log the contents of documents being processed.** Log identifiers and sizes,
  not payloads.
- **Security issues are reported privately.** Do not open a public issue describing an
  unpatched vulnerability in this project, and do not describe an unfixed weakness in
  a commit message, changelog or README.

## Working Environment

- **Never run `npm`, `yarn` or `npx` directly on Joe's machine.** If Node tooling is
  ever needed, run it in Docker.
- `dotnet build`, `dotnet test` and `dotnet run` are fine to run locally.
- The `gh` CLI is installed but not on `PATH`. Prefix commands with:
  `export PATH="$PATH:/c/Program Files/GitHub CLI"`
